# Engineering audit

Audit date: 2026-10-20. Scope includes source inspection, local tests/build/import/syntax validation, isolated replica-set and browser smoke tests, and read-only production HTTP probes. No production database or credentials were accessed, and no deployment or production mutation was performed.

Priorities rank severity first, then exploitability (anonymous versus authenticated access), affected-action frequency, user impact, and remediation effort. Critical is used for direct data-integrity or reward-abuse paths; High for authentication, privacy, or cross-instance security controls; Medium for bounded reliability, data consistency, or usability defects. The risk/impact column records the concrete consequence and the remaining-work column identifies evidence still unavailable.

| Priority | Confirmed finding and code path | Risk / impact | Change | Remaining work |
|---|---|---|---|---|
| Critical | `POST /focus/harvest` accepted client duration and timestamps, created completed sessions, then incremented Spice on every request. | A logged-in user could claim rewards without waiting; retries could duplicate rewards. | Replaced the flow with server-created running sessions, server-clock completion checks, a transaction for completion and Spice, pause/resume/recovery, and a unique active-session index. Legacy harvest now returns 410. | Replica-set integration tests cover transactional idempotent reward completion; standalone MongoDB cannot complete harvest requests. |
| High | Refresh rotation read a valid token, revoked it, then issued another token in separate operations. | Concurrent refresh requests could both succeed. | Rotation now atomically consumes a non-revoked, unexpired token before issuing its successor. | Replica-set integration test confirms concurrent consumption succeeds once. |
| High | Google OAuth linked an existing account by email without requiring the provider email to be verified. | Unverified identity could attach to an existing account. | Only verified Google email addresses proceed to account lookup/linking. | Exercise Google OAuth callback with test identities and confirm provider profile shape. |
| High | Google OAuth used Passport's default no-op state store, so the callback was not bound to the browser that started sign-in. | An attacker could initiate OAuth and cause a victim browser to complete a login flow the victim did not start. | Added a cryptographically random 10-minute OAuth state in an HttpOnly, SameSite=Lax cookie and constant-time callback validation; mismatched or missing state is rejected and the cookie is cleared. | Unit tests cover cookie issuance and state mismatch. Production reports Google OAuth enabled and redirects to accounts.google.com, but the current live redirect has no state parameter or state cookie; the fixed flow remains local until an authorized release. A full callback still requires a test identity. |
| High | Local user records defaulted `googleId` to explicit `null` while the field had a unique sparse index. | MongoDB indexes explicit null values in a sparse index, so creating multiple local users could collide on the unique `googleId` key. | Removed the null default so local accounts omit the optional field; linking Google continues to set a string ID. The replica-set fixture now creates multiple simultaneous local users. | Existing null-valued account records and the current production index still need observation in the owner-controlled deployment. |
| Medium | Registration checked for an existing email and then inserted in a separate operation. | Concurrent requests for the same address could race on the unique index and turn the expected conflict into a generic 500. | MongoDB duplicate-key insertion errors now map to the same 409 conflict response as the pre-insert lookup; a regression test confirms tokens are not issued after the collision. | The deterministic race passes against a local replica set; production index state remains uninspected. |
| High | Socket middleware accepted connections without a token. | Unauthenticated sockets could connect and receive any future global emissions. | Socket connections now require a valid access token and are only joined to that user's room. | Local live Socket.IO tests cover anonymous rejection, token expiry, and user-derived room membership; production socket behavior is not verified. |
| Medium | The browser opened a socket with its initial access token but did not refresh credentials after the server disconnected it at token expiry; missed events had no HTTP resynchronization path. | Realtime updates could silently stop after expiry or a network interruption until a page-level action happened to reload data. | The socket hook now refreshes the shared session on auth rejection/server expiry, updates the socket auth token without dropping account identity, reconnects, and refetches dashboard data after reconnect. Client unit tests cover token-expiry recovery, transient network reconnect, and failed refresh; CI runs these tests. | Browser E2E has not forced a real expiry and reconnect end-to-end. |
| High | Mentat had only OpenAI and heuristic selection, no output validation, and sent the full dashboard context to OpenAI. | Requested Gemini path absent; unbounded provider output and excess data disclosure. | Added Gemini adapter using the official SDK Interactions API with `response_format` JSON Schema, `store: false`, independently validated output, compact context, SDK-compatible abort signal, timeout, one transient retry, explicit heuristic fallback, and shared MongoDB budgets. Preserved OpenAI and heuristic routing; signals remain authoritative server calculations. Google's current model page lists `gemini-3.5-flash-lite` as stable and supporting structured outputs ([model](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite), [structured outputs](https://ai.google.dev/gemini-api/docs/structured-output)). | Provider calls are mocked; no live credentials or quota check. |
| High | API and Mentat request ceilings lived in process-local state. | Multiple Render instances could each enforce an independent limit, weakening the global ceiling and allowing distributed overuse. | Replaced process-local production buckets with atomic MongoDB counters keyed by SHA-256 fingerprints; fixed-window expiry uses a TTL index. Separate middleware/service instances share counters, and requests fail closed with 503 if the database cannot enforce limits. | Replica-set integration covers API and Mentat sharing; production multi-instance behavior has not been exercised. |
| High | The checked-in Render Blueprint described a native Node service with a name that did not match the live Docker service; the Dockerfile and Vercel project were pinned to discontinued Node.js 20. | Blueprint sync could target a new service instead of the production service, while the next Vercel build failed before compiling. | Blueprint now matches the live Render service name, main branch, Docker runtime, Singapore region, and Docker context; the image and package engines use Node.js 24, CI uses Node 24, and the Vercel project Node setting was updated to 24.x. Added `.dockerignore`; the Blueprint was schema-validated and not synced. | A Render Docker build and a successful Vercel build after the version change remain unverified; the feature-branch Vercel preview before the change failed with the Node 20 discontinuation error. |
| Medium | Focus and distraction aggregation emitted only active days, grouped dates in server local time, and productivity averaged daily means without weighting by sessions. | Empty days disappeared and weekly productivity could be biased. | Series now fill seven UTC days; date boundaries use UTC; productivity weights each daily average by session count. | Existing chart and dashboard calculations need additional product review; UTC may not match a user's chosen timezone. |
| Medium | Production Morgan `dev` logging included request URLs; error handler logged full exceptions. | Query-string identifiers or provider errors could enter logs. | Production access logging omits URL; production error logs include only status and error type, and 5xx responses are generic. | Review Render log retention and current deployment configuration. |
| Medium | Database startup used Mongoose `syncIndexes()` and dropped named legacy indexes. | Startup could remove indexes outside the declared schema and cause unexpected production query regressions. | Startup now creates required refresh-token indexes without reconciling or dropping unrelated indexes. SIGINT/SIGTERM close Socket.IO and MongoDB cleanly; startup/shutdown logs no longer print exception details. | Shutdown path is reviewed and syntax/import checked; live Render termination was not exercised. |
| High | `npm run seed` deleted every user, team, session, distraction, token, and roadmap record in its configured database before inserting demo accounts. | Running the development helper with a production URI could permanently erase production account and activity data. | Seeding now fails in production, rejects non-loopback MongoDB hosts, and requires `ARRAKIS_ALLOW_DESTRUCTIVE_SEED=true` before connecting. The local reset procedure is documented; guard tests cover production, missing opt-in, remote/malformed URIs, and the allowed local target. | No production database was contacted; local seeding itself was not run because it intentionally deletes the target database contents. |
| Medium | Leaderboard queries returned email addresses; team member population also selected them, and client-supplied limits were uncapped. | Private account information was disclosed to authenticated users and queries could be oversized. | Removed email from leaderboard/team population and response; leaderboard limits are clamped to 1–50. Rate-limit IP identity now trusts Express's configured `req.ip` rather than the spoofable first forwarded header. | Privacy response behavior has service/controller coverage; limiter boundaries and shared MongoDB storage have unit and replica-set integration tests. |
| Medium | CORS rejected an untrusted `Origin` without an HTTP status, so Express returned 500 although the browser correctly received no `Access-Control-Allow-Origin` header. | Expected cross-origin denials looked like server faults and could pollute error monitoring. | CORS now returns a generic 403 `ApiError` without echoing the supplied origin; focused tests cover configured, absent, and untrusted origins. | Read-only production probe confirmed the currently deployed backend still returns 500 for an untrusted origin; the fix remains local until a reviewed deployment. |
| Medium | `ProfileService.updateSettings` spread a Mongoose preferences subdocument directly into an update object. | Mongoose internal fields were included; settings requests returned success while persisted preferences stayed unchanged. | Convert the subdocument to a plain object before merging. Replica-set integration asserts stored strict mode, warning threshold, and blocked sites after save. | Broader settings API validation tests remain useful. |
| Medium | The platform had no account export or user-requested deletion path despite retaining profile, focus, distraction, roadmap, refresh-token, and team references. | Users could not retrieve their stored activity or remove their account data without an administrator; naive deletion of a team owner could orphan ownership and aggregates. | Added a protected JSON export and deletion flow requiring recent authentication, matching email, local-password confirmation (or explicit phrase for Google accounts), and a transaction that removes personal records and refresh tokens while preserving team consistency. Team-owner deletion hands ownership and aggregates to the oldest remaining member. Owner selected retention until the user deletes their account; no age-based active-account purge runs. | Verify operational backup retention separately; it is controlled by the production database provider, not this repository. |
| Medium | The distraction API accepted URL and page-title fields and wrote them into new activity records, even though current extension builds stripped those fields before synchronization; a full URL could also be placed in the `site` field. | Older or third-party clients could persist full browsing paths and page titles, including sensitive query parameters. | The API continues accepting legacy URL/title fields but discards them; it normalizes `site` values to an HTTP(S) hostname before storage. Existing records are preserved and remain exportable/deletable. Regression tests cover legacy fields and URL normalization. | Existing stored URL/title values are not automatically purged; the owner-selected policy retains active-account history until account deletion. |
| Medium | Team creation and membership changes updated team member IDs, user team references, and leaderboard totals in separate writes. | A failed or concurrent membership change could leave users in multiple teams or stale aggregate values. | Create and join flows now re-read the user in a MongoDB transaction, update membership references together, and recalculate affected totals before commit. The replica-set test races two joins and verifies exactly one membership and matching Spice/streak aggregates. | Live team leaderboard behavior has not been exercised against the production deployment. |
| Medium | Login, registration, profile, settings, and manual dashboard forms had labels without control associations; dashboard controls relied only on placeholder text, and the 404 page nested links around buttons. | Screen readers could miss field names and nested interactive elements created invalid navigation semantics. | Associated labels with form controls, added accessible names to unlabeled controls and autocomplete hints, and made 404 actions direct links. | A one-off Chrome/axe-core scan now covers key public and authenticated states; axe is not wired into CI. |
| Medium | The dashboard account-menu trigger overrode its accessible name with text that did not match all visible responsive labels, including the avatar initials. | The spoken control name could disagree with the visible button label, failing WCAG label-in-name checks. | Replaced the override with a screen-reader-only name containing the initials, operative name, and menu purpose; decorative duplicate text is hidden from the accessibility tree. | Chrome/axe-core scans pass for dashboard, mobile navigation, account menu, and logout confirmation at 360px and 1365px; CI does not yet run axe. |
| Medium | Confirmation and mobile navigation dialogs did not move or trap keyboard focus, restore focus on close, or close on Escape; some controls also lacked a shared visible focus indicator. | Keyboard and assistive-technology users could move focus behind an open dialog or lose their place after it closed. | Added shared dialog focus management, Escape and backdrop closing, focus restoration, tab trapping, and a global `:focus-visible` outline. Added JSDOM and headless Chrome regression coverage for focus entry, tab wrapping, Escape, and focus restoration. Logout confirmation now returns focus to the account-menu trigger when its menu item is removed. | Automated headless keyboard checks pass; manual assistive-technology and keyboard review remains. |
| Medium | The application used Framer Motion and smooth scrolling without respecting the operating system's reduced-motion preference. | Users who request reduced motion still received animated transforms, transitions, and smooth scrolling. | Wrapped the app in Framer Motion's `MotionConfig reducedMotion="user"` and added a reduced-motion CSS rule for native animation, transition, and scroll behavior. | Build verification confirms the integration compiles; manual operating-system preference/browser review remains. |
| Medium | The refresh interceptor coalesced concurrent refreshes after API 401 responses, but the React StrictMode auth-bootstrap effect called the refresh endpoint directly. Two refreshes could consume the same cookie; same-second JWTs also lacked a unique identifier and could collide in the token hash index. The shared client helper also initially returned a different Axios response shape than the configured client. | A development page remount or simultaneous bootstrap could invalidate a valid browser session, successor token creation could fail on a duplicate hash, or the client could fail to read a valid access token. | Auth bootstrap and the 401 interceptor now share one in-flight refresh request and retain the existing response envelope. Refresh JWTs include a random `jti`; regression coverage verifies same-second uniqueness. | None for the reproduced registration-to-profile refresh path; broader Google OAuth callback testing remains unavailable without credentials. |
| Medium | Extension telemetry sent page URLs and titles; blocked matching also searched the whole URL. Failed sync did not preserve the flushed duration, queue retries stopped without new activity or a browser restart, and the tracked ZIP omitted the background worker's imported `domainRules.js`. The extension also relied on manually pasted short-lived access tokens. | Unnecessary browsing details were stored; URL text could cause false-positive blocking; queued data could remain stuck; packaged extension failed module resolution; extension authentication expired without recovery. | Current source strips legacy titles/URLs from local buffers, sends hostname/duration only, matches hostname/subdomains only, retries stable event IDs using persisted alarms with bounded backoff, eight attempts and a one-day TTL, and limits buffered hosts. The authenticated Arrakis app now hands the current short-lived token to the extension on trusted origins; queued events wait for reauthentication and account changes clear the queue. The ZIP includes the imported module and is checked in CI against source. | Isolated Chromium and Edge tests cover blocking, restart behavior, account token handoff, logout token clearing, and account-switch queue isolation. Normal-profile behavior and store installation still need manual Chrome/Edge verification. |
| Medium | Blocked destinations were copied into the visible extension block-page query string, including any original URL query parameters. | Sensitive parameters could remain in browser-visible extension URLs and browser diagnostics/history. | Block destinations now stay in `chrome.storage.session` under a random context ID for at most ten minutes; the extension URL contains only that ID, and an alarm removes the record at expiry or it is cleared after override. | Requires Chrome 102+ session storage; browser install and override lifecycle still need Chrome/Edge testing. |
| Medium | Extension installation initialized defaults asynchronously while the popup wrote settings directly to local storage; a save immediately after install could be overwritten by the late defaults write. Concurrent block checks could also redirect the same tab more than once. | First-run settings could be lost and duplicate temporary destination contexts could be created. | Defaults initialization is now shared and awaited by background reads/writes; popup settings use validated background messages. Blocking checks verify the current tab URL and coalesce redirects per tab. | Chromium and Edge smoke tests passed, including Edge extension reload; store installation and normal-profile verification remain. |

## Baseline and validation gaps

The repository initially had no tests or server test script. The unit suite covers auth-service and auth-controller behavior, verified Google OAuth linking, auth middleware identity/role checks, environment bounds, focus reward rules, service-level concurrency and idempotent completion retries, analytics calculations, Gemini response validation and timeout behavior, profile input/settings behavior, roadmap phase progression, extension host matching, override expiration, pending-sync alarm scheduling, Storm event idempotency at the service boundary, rate-limit boundaries, live Socket.IO auth/room/expiry behavior, refresh-token concurrent consumption, and preservation of original authentication time across refresh. Registration also bounds skill count and name length. Replica-set integration coverage exercises focus reward transactions, persisted profile/settings and roadmap changes, refresh-token consumption, concurrent team membership, account export redaction, and transactional account deletion/team-owner handoff. The frontend build updates tracked `client/dist/index.html`; that generated change was restored after verification to preserve its existing site-verification metadata. The first new provider test exposed an abort/timeout classification issue, which was fixed before rerunning the suite.

The client has migrated to Tailwind CSS 4.3.3 with its Vite plugin and an explicit legacy config load for the existing design tokens. The generated stylesheet builds with the repository's custom utilities. The README documents Tailwind 4's browser minimums: Safari 16.4+, Chrome 111+, and Firefox 128+. Full and production dependency audits are clean for both applications.
